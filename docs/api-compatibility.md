# API compatibility policy

The production REST API is versioned under `/api/v1`. The version segment identifies the major API contract. Changes inside the same major version should be backward compatible.

## Non-breaking changes

These changes may be made within `/api/v1`:

- adding optional request fields
- adding response fields
- adding new endpoints
- adding new enum values when clients can safely ignore unknown values
- adding optional query parameters
- adding response headers
- tightening documentation without changing runtime behavior

## Breaking changes

These changes require a new major version, such as `/api/v2`, or an explicit migration plan:

- removing or renaming endpoints, fields, query parameters, or headers
- changing field types or formats
- adding required request fields
- changing authentication or authorization semantics
- changing success or error response shapes
- changing pagination defaults in a way that hides records from existing clients
- changing money precision or date/time semantics

## Current contract conventions

- API routes use path major versioning: `/api/v1/...`.
- Error responses use a stable envelope:

```json
{
  "error": {
    "code": "ValidationFailed",
    "message": "Request body is required.",
    "requestId": "..."
  }
}
```

- Responses generated by the API helpers include `X-Request-Id`.
- Clients may send `X-Request-Id`; otherwise the API generates one.
- Mutating finance endpoints support `Idempotency-Key` for safe retries.
- List endpoints support opt-in pagination with `limit` and `offset`.
- Existing unpaginated list calls continue to return arrays for `/api/v1` compatibility.

## Deprecation guidance

When `/api/v2` is introduced, `/api/v1` should remain available during a documented migration window. Removal should require release notes, client migration instructions, and a planned cutoff date.
